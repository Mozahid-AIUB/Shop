# Phase 11 — Fraud Guard (COD ঝুঁকি)

**লক্ষ্য:** COD অর্ডার পাঠানোর **আগে** ঝুঁকির আভাস দেওয়া, যাতে অ্যাডমিন
সন্দেহজনকগুলোতে ফোন করে নিশ্চিত হতে পারে।

**কেন দরকার:** বাংলাদেশে COD-ই প্রধান পেমেন্ট, আর কিছু পণ্যে ফেরতের
ক্ষতিটা দ্বিগুণ — কাস্টম ছাপা পণ্য (নাম/ডিজাইন ওই ক্রেতার), সিল করা
খাবার বা প্রসাধনী, মেয়াদ-সংবেদনশীল পণ্য — ফেরত এলে আর কাউকে বেচা
যায় না। তার উপর কুরিয়ারের যাওয়া-আসার খরচও যায়।

**এই phase-এ নয়:** কুরিয়ারের return history API (Steadfast fraud check) —
API key লাগবে, Phase 10-এর সাথে হবে।

## ১. সবচেয়ে গুরুত্বপূর্ণ সিদ্ধান্ত: ব্লক করা হবে না

| প্রশ্ন | সিদ্ধান্ত | কেন |
|---|---|---|
| স্কোর বেশি হলে? | **শুধু ফ্ল্যাগ**, ব্লক নয় | নিচে দেখো |
| কে দেখবে? | staff (admin board-এ) | ফোন করে যাচাই করাই উদ্দেশ্য |
| কখন হিসাব হবে? | checkout-এর সময়, একবার | অর্ডারের সাথে সংরক্ষিত থাকবে |
| স্কোর বদলালে পুরোনো অর্ডার? | বদলাবে না | ওই সময়ের সিদ্ধান্ত ওই সময়ের তথ্যে |

**কেন ব্লক নয় — এটাই এই phase-এর মূল কথা:**

ভুল দুই রকম হতে পারে, কিন্তু দুটোর দাম এক নয়:

- **জালিয়াতকে ছেড়ে দিলে:** এক অর্ডারের পণ্য + কুরিয়ার খরচ যায়।
  টাকার অঙ্কে ছোট, আর ঘটনাটা তুমি দেখতে পাও।
- **আসল ক্রেতাকে ব্লক করলে:** সে চিরতরে চলে যায়, বন্ধুদের বলে, আর
  **তুমি কোনোদিন জানতেই পারো না** — কারণ ব্লক হওয়া ক্রেতা অভিযোগ
  করতে আসে না, চুপচাপ অন্য দোকানে যায়।

দ্বিতীয় ক্ষতিটা অদৃশ্য আর স্থায়ী। তাই সিস্টেম কখনো নিজে থেকে "না"
বলবে না — শুধু বলবে "এটা একটু দেখে নিন"। সিদ্ধান্ত মানুষের।

## ২. ঝুঁকির সংকেত (সব নিজের ডেটা থেকে)

প্রতিটা সংকেতের একটা পয়েন্ট আছে। যোগফলই স্কোর (০-১০০)।

| সংকেত | পয়েন্ট | কেন এই ওজন |
|---|---|---|
| আগের অর্ডার বাতিল/ফেরত হয়েছে | প্রতিটায় ২৫, সর্বোচ্চ ৫০ | **সবচেয়ে বিশ্বস্ত সংকেত** — অতীত আচরণই ভবিষ্যতের সেরা আভাস |
| একই ফোনে ২৪ ঘণ্টায় ৩+ অর্ডার | ২০ | স্বাভাবিক ক্রেতা এক দিনে এত অর্ডার করে না |
| নতুন অ্যাকাউন্ট (৭ দিনের কম) + বড় COD | ২০ | সবচেয়ে বেশি ক্ষতি এখানেই হয় |
| একই ঠিকানা, আলাদা অ্যাকাউন্ট | ১৫ | ব্লক এড়াতে নতুন অ্যাকাউন্ট খোলার চিহ্ন |

**"বড় COD" কত?** `FRAUD_LARGE_ORDER_PAISA`, ডিফল্ট ৫০০০ টাকা।
`.env`-এ বদলানো যাবে — যে কোড কিনবে তার দোকানের গড় অর্ডার আলাদা হবে।

**সফল ডেলিভারি স্কোর কমায়:** প্রতিটা সফল অর্ডারে −১৫ (সর্বোচ্চ −৪৫)।
না রাখলে পুরোনো ভালো ক্রেতা একবার বাতিল করলেই চিরকাল সন্দেহভাজন
থেকে যেত।

### স্তর

| স্কোর | স্তর | অ্যাডমিন কী দেখবে |
|---|---|---|
| ০-২৪ | `LOW` | কিছু না |
| ২৫-৪৯ | `MEDIUM` | হলুদ চিহ্ন |
| ৫০+ | `HIGH` | লাল চিহ্ন + "ফোন করে নিশ্চিত করুন" |

## ৩. Schema

```prisma
model FraudCheck {
  id        String   @id @default(cuid())
  orderId   String   @unique
  score     Int
  level     FraudLevel
  /// কোন কোন কারণে স্কোর — অ্যাডমিন যেন কারণ দেখতে পায়
  reasons   Json
  createdAt DateTime @default(now())
  order     Order    @relation(...)
}
```

**কেন `reasons` সংরক্ষণ করা হয়:** শুধু "৬৫ স্কোর" দেখালে অ্যাডমিন কিছু
করতে পারে না। "আগে ২টা অর্ডার ফেরত দিয়েছে" দেখলে সে জানে কী জিজ্ঞেস
করতে হবে। ব্যাখ্যাহীন স্কোর মানুষ হয় অন্ধভাবে মানে, নয় উপেক্ষা করে —
দুটোই খারাপ।

**কেন `CustomerRiskProfile` টেবিল নয়** (TODO-তে ছিল): স্কোর অর্ডারের
সময়কার অবস্থা, স্থায়ী বৈশিষ্ট্য নয়। আলাদা profile রাখলে সেটা বাসি
হতো আর "কেন এই স্কোর" প্রশ্নের উত্তর মিলত না। দরকার হলে অর্ডার থেকে
যেকোনো সময় হিসাব করা যায়।
