# Phase 10 — Courier

> অর্ডার কুরিয়ারে পাঠানো, ট্র্যাক করা, আর অবস্থা নিজে থেকে আপডেট হওয়া।
>
> **সেটআপ পুরোটাই অ্যাডমিন প্যানেল থেকে** — `.env`-এ শুধু একটা
> এনক্রিপশন চাবি, কোনো কুরিয়ারের key নয়।

## সবচেয়ে জরুরি কথা

**`MANUAL` (নিজের ডেলিভারি) আজই কাজ করে, কোনো key ছাড়াই।**

এটা ইচ্ছাকৃত নকশা। যে ব্যবসায়ী এই কোড কিনবে, তার Steadfast বা
Pathao-র সাথে চুক্তি হতে দিন-সপ্তাহ লাগবে। `MANUAL` না থাকলে
ততদিন দোকান অর্ডার নিতে পারত কিন্তু "পাঠানো হয়েছে" বলার কোনো
উপায় থাকত না।

`MANUAL` অ্যাকাউন্টটা **migration-এ তৈরি হয়**, seed-এ নয় — CI
seed চালায় না, আর যে ব্যবসায়ী শুধু `db:deploy` চালাবে সেও না।

## Steadfast তৈরি — Pathao, RedX, Carrybee বাকি

**Steadfast adapter লেখা হয়ে গেছে** (`providers/steadfast.provider.ts`),
মালিকের merchant dashboard-এর API guide ধরে — অনুমান ছাড়া।

বাকি তিনটার auth একেবারে আলাদা, আর আসল ডকুমেন্টেশন merchant
dashboard-এ থাকে (পাবলিক সার্চে শুধু third-party wrapper, তাদের
মধ্যেই অমিল):

| কুরিয়ার | auth | যা জানা গেছে |
|---|---|---|
| Steadfast | api-key + secret-key header | `portal.packzy.com/api/v1`, `POST /create_order` |
| RedX | `API-ACCESS-TOKEN: Bearer <jwt>` | `openapi.redx.com.bd`, `POST /parcel` |
| Pathao | OAuth 2.0, টোকেনের মেয়াদ শেষ হয় | client id + secret + username + password |
| Carrybee | Client-ID + Client-Secret + Client-Context | v2.0, sandbox আলাদা |

অনুমান করে লিখলে চারটাই ভুল হতো, আর key বসানোর পর ব্যর্থ হতো —
তখন বোঝাই যেত না ভুলটা key-তে না কোডে।

**adapter লিখতে যা লাগবে:** কুরিয়ারের merchant dashboard-এর API
ডকুমেন্টেশন (সাধারণত ওখানেই থাকে), আর sandbox credential।
`COURIER_CREDENTIAL_FIELDS`-এ প্রতিটার মাঠগুলো আগেই লেখা আছে।

নতুন adapter যোগ করতে দুটো জায়গা: `providers/` ফোল্ডারে ফাইল, আর
`CourierRegistry`-র constructor। বাকি কোনো ফাইল ছুঁতে হবে না।

## Steadfast — ডক থেকে যা শেখা গেল

তিনটা জিনিস অনুমান করলে ভুল হতো, আর দুটোর দাম টাকায়:

| তাদের নিয়ম | অনুমান করলে |
|---|---|
| `cod_amount` **টাকায়**, paisa-তে নয় | কুরিয়ার **১০০ গুণ** টাকা তুলতে যেত |
| `delivered_approval_pending` ≠ `delivered` | টাকা না পেয়েই অর্ডার সম্পন্ন দেখাত |
| একই `invoice` দুবার নেয় না | ফেরত আসা পণ্য **আর পাঠানোই যেত না** |

দুই নম্বরটা তাদের ডকেই লেখা: *"Do not settle your books on it —
wait for delivered, partial_delivered or cancelled."* রাইডার বলেছে
পৌঁছেছে, কিন্তু তাদের হিসাব বিভাগ নিশ্চিত করেনি। তাই
`_approval_pending`-ওয়ালা সব অবস্থা আমাদের দিকে `IN_TRANSIT`।

তিন নম্বরটা **আমাদের নিজের কোডের একটা বাগ ধরিয়ে দিল।** ফেরত আসা
অর্ডার আবার পাঠানোর অনুমতি আছে, কিন্তু তখন একই অর্ডার নম্বর যেত আর
Steadfast না বলত। এখন `ParcelRequest.parcelReference` আলাদা:
দ্বিতীয় পার্সেলে `-R2`, তৃতীয়তে `-R3` — কুরিয়ারের প্যানেলে দেখেই
বোঝা যায় কোনটা পুনঃপ্রেরণ।

### আরো তিনটা

- **`cancelled` → `RETURNED`, `CANCELLED` নয়।** ডকে লেখা "The
  parcel comes back to you"। আমাদের `CANCELLED` মানে পাঠানোই হয়নি;
  মিলিয়ে ফেললে ফেরত আসা পণ্য কেউ জানত না আর স্টকেও যোগ হতো না।
- **`hold`, `exceptional`, `unknown` কোনো স্বাভাবিক অবস্থায় map
  করা হয় না** — ডকে তিনটাতেই "Contact support"। map করলে অ্যাডমিন
  ভাবত সব ঠিক চলছে, অথচ পার্সেল আটকে বা হারিয়ে গেছে।
- **`{ } ; < > $` আগেই সরানো হয়** — তারা নিজে ফাঁকা জায়গায় বদলে
  দেয়। না সরালে আমাদের রেকর্ড আর তাদের রেকর্ড আলাদা হয়ে যেত, আর
  অভিযোগের সময় কোনটা আসল তা বলা যেত না। লম্বা মানও আগেই কাটা হয়
  (ঠিকানা ৪৯০, নাম ১০০) — তারা কাটলে ঠিকানা অর্ধেক হয়ে পার্সেল
  পৌঁছাত না।

### retry-র নিয়ম

ডকে লেখা: একই ঠিকানা থেকে ৫ মিনিটে ১০ বার ভুল key দিলে **৬০ মিনিট**
আটকে যায়, ঠিক key দিলেও।

| কোড | retry? | কেন |
|---|---|---|
| 401 / 403 | **না** | key বা অ্যাকাউন্টের সমস্যা; লুপে retry করলে এক ঘণ্টা আটকে যেত |
| 422 | না | মাঠ ভুল — অ্যাডমিনকে **কোন মাঠ** সেটা বলা হয় |
| 429 | হ্যাঁ | অপেক্ষা করলে কাজ হবে |
| 5xx | হ্যাঁ | ডকে লেখা duplicate invoice refused, তাই দুবার বুক হবে না |

### ২০০-র ভেতরেও ব্যর্থতা

ডকে স্পষ্ট: *"Some endpoints report a per-item failure inside a 200
— always read the body."* শুধু HTTP কোড দেখলে পার্সেল তৈরি হয়নি অথচ
আমরা সফল ধরে অর্ডার `SHIPPED` করে দিতাম, আর কেউ পণ্যটা নিতে আসত না।

### যা Steadfast-এ নেই

পার্সেল **বাতিলের API নেই**। `create_return_request` আছে (ফেরত আনা),
কিন্তু সেটা বাতিল নয় — ভুল endpoint ডেকে "বাতিল হয়েছে" বলা বিপদের:
অ্যাডমিন ভাবত পার্সেল আটকানো গেছে, অথচ সেটা ক্রেতার কাছে চলেই যেত।
তাই `cancel()` স্পষ্ট করে বলে কী করতে হবে।

বুকিংয়ের সময় চার্জও জানায় না, তাই `feePaisa` `null` — ভুয়া সংখ্যা
বসানোর চেয়ে `null` ভালো, তখন অ্যাডমিন জানে payout রিপোর্ট থেকে
মেলাতে হবে।

## নিরাপত্তা — দুটো আসল ঝুঁকি

### ১. key ফাঁস

কুরিয়ারের key ব্যবসার **নিজের অ্যাকাউন্টে** বাঁধা। হাতে পেলে যে
কেউ ওই অ্যাকাউন্ট দিয়ে পার্সেল পাঠাতে পারে, আর COD-র টাকার
হিসাবও ঘেঁটে দিতে পারে।

| রক্ষা | কীভাবে |
|---|---|
| DB-তে এনক্রিপ্ট করা | AES-256-GCM (`src/common/secret-box.ts`) |
| মূল চাবি DB-তে নয় | `.env`-এ `COURIER_SECRET_KEY` |
| response-এ key ফেরে না | শুধু শেষ ৪ অক্ষর (`••••abcd`) |
| ছেঁড়াখোঁড়া ciphertext ধরা পড়ে | GCM auth tag — decrypt throw করে |

**GCM, CBC নয়** — ইচ্ছাকৃত। CBC-তে কেউ DB-র ciphertext বদলালে
চুপচাপ আলতু-ফালতু মান ফিরত আর আমরা সেটা নিয়ে কুরিয়ারে call
করতাম। GCM-এ decrypt ব্যর্থ হয়।

**চাবিটা হারালে সব key আবার বসাতে হবে** — পুরোনো মান আর খোলা
যাবে না। `.env`-এর ব্যাকআপ রাখা জরুরি।

production-এ চাবি না দিলে **অ্যাপ চালু হয় না**। একটা ফাঁকা
default বসালে সব দোকান একই চাবি ব্যবহার করত, আর একজনের DB ফাঁস
হলে সবার key খোলা যেত।

### ২. ভুয়া webhook

secret ছাড়া webhook নিলে যে কেউ "DELIVERED" পাঠিয়ে অর্ডার
ডেলিভারড দেখাত, আর **COD-র টাকা না পেয়েই হিসাব মিলে যেত**। ভুয়া
রিটার্নও পাঠানো যেত, যা ক্রেতার ঝুঁকির স্কোর নষ্ট করত।

- **secret না বসানো থাকলে webhook ৪০১** — adapter-এ পৌঁছায়ই না
- তুলনা **সময়-নিরপেক্ষ** (`timingSafeEqual`) — নইলে উত্তরের সময়
  মেপে অক্ষর ধরে ধরে secret অনুমান করা যেত
- HMAC **কাঁচা body-তে** — JSON আবার stringify করলে মাঠের ক্রম
  বদলে signature মিলত না

`src/modules/courier/webhook-guard.ts`-এ সব এক জায়গায়, কারণ
প্রত্যেক adapter নিজে লিখলে কোথাও একটা `===` বসে যেত আর সেই
একটা জায়গা দিয়েই ভুয়া webhook ঢুকত।

## যা তৈরি হলো (API)

### সেটআপ — `SUPER_ADMIN` only

| Method | Path | কী করে |
|---|---|---|
| GET | `/admin/couriers` | তালিকা, **key ছাড়া** |
| GET | `/admin/couriers/supported` | কোনগুলোর adapter তৈরি |
| POST | `/admin/couriers` | নতুন কুরিয়ার |
| PATCH | `/admin/couriers/:id` | বদলানো |
| DELETE | `/admin/couriers/:id` | মোছা |

key দিয়ে টাকার হিসাব বদলানো যায়, তাই এটা স্টাফের কাজ নয়।

### পার্সেল — `SUPER_ADMIN` + `ORDER_MANAGER`

| Method | Path | কী করে |
|---|---|---|
| POST | `/admin/orders/:orderNumber/dispatch` | কুরিয়ারে পাঠানো |
| PATCH | `/admin/shipments/:id/status` | অবস্থা হাতে বদলানো |

`ORDER_MANAGER`-ও পারে: পার্সেল পাঠানো দৈনিক কাজ, শুধু মালিকের
হাতে রাখলে সে ছুটিতে গেলে অর্ডার আটকে থাকত।

### webhook — খোলা, কিন্তু secret দিয়ে যাচাই

| Method | Path |
|---|---|
| POST | `/courier-webhook/:courier` |

`:courier` = `steadfast`, `pathao`, `redx`, `carrybee`।

**২০০ ফেরে প্রায় সবসময়**, ইচ্ছাকৃতভাবে। কুরিয়ার ত্রুটি পেলে একই
webhook বারবার retry করে আর তাদের queue আটকে যায়। ব্যতিক্রম: ভুল
secret (৪০১) আর অজানা কুরিয়ার (৪০৪) — দুটোই সেটআপের ভুল, retry
করে ঠিক হবে না।

ভুল signature আর "এই ঘটনা আমাদের কাজে লাগে না" — দুটোই ২০০ পায়,
আলাদা করা হয় না। আলাদা করলে ভুয়া webhook পাঠিয়ে signature অনুমান
করার চেষ্টা সহজ হতো।

## নকশার সিদ্ধান্ত

### অর্ডার আর পার্সেল আলাদা টেবিল

একটা অর্ডার ফেরত এসে আবার পাঠানো হতে পারে — তখন দুটো পার্সেল,
একই অর্ডার। `Order`-এ ট্র্যাকিং নম্বর রাখলে দ্বিতীয়বারে প্রথমটার
হিসাব হারিয়ে যেত, আর "কতবার পাঠিয়ে ফেরত এলো" কখনো জানা যেত না।

### credential এক কলামে, এনক্রিপ্টেড JSON

আলাদা কলাম নয়, কারণ চারটা কুরিয়ারের মাঠ একেবারে আলাদা
(Steadfast-এ ২টা, Pathao-তে ৫টা)। আলাদা কলাম রাখলে অর্ধেক কলাম
সবসময় `null` থাকত আর নতুন কুরিয়ার যোগ করতে migration লাগত।

### row আগে, কুরিয়ারে কল পরে

`Shipment` row কুরিয়ারে কল করার **আগে** তৈরি হয়। উল্টো করলে
কুরিয়ারে পার্সেল তৈরি হয়ে যেতে পারত অথচ আমাদের দিকে কিছুই নেই —
পার্সেল গেছে, আমরা জানি না।

কুরিয়ারের API কল **transaction-এর বাইরে**: ভেতরে রাখলে তাদের ধীর
উত্তরের জন্য DB-র লক ধরে বসে থাকতে হতো।

### ফেরত এলে অর্ডার বাতিল হয় না

| পার্সেল | অর্ডার |
|---|---|
| পিকআপ / পথে | `SHIPPED` |
| পৌঁছেছে | `DELIVERED` |
| **ফেরত** | **বদলায় না** |
| বাতিল | বদলায় না |

ফেরত মানে ক্রেতা নেয়নি, কিন্তু পণ্য দোকানে ফিরেছে আর টাকার হিসাব
এখনো বাকি। রিফান্ড? আবার পাঠানো? সিদ্ধান্তটা মানুষের।

### পৌঁছে যাওয়া পার্সেল পিছিয়ে যায় না

কুরিয়ারের webhook **ক্রমে আসে না**। দেরিতে আসা "IN_TRANSIT" পরে
এলে পার্সেল পিছিয়ে যেত আর অ্যাডমিন ভাবত হারিয়ে গেছে।

একই অবস্থা আবার এলে ত্রুটি নয়, চুপচাপ মেনে নেওয়া হয় — duplicate
webhook স্বাভাবিক ঘটনা। `@@unique([shipmentId, status, occurredAt])`
ইতিহাসে দুবার লেখা আটকায়।

### অজানা অবস্থায় অনুমান নয়

কুরিয়ার নতুন শব্দ পাঠালে (`"teleported"`) পার্সেল যেমন ছিল তেমনই
থাকে, আর কাঁচা মান `rawStatus`-এ জমা হয়। অনুমান করে `DELIVERED`
ধরে নিলে টাকা না পেয়েই অর্ডার সম্পন্ন দেখাত।

## COD-র অঙ্ক

```
পেমেন্ট হয়ে গেছে  →  কুরিয়ার তুলবে ০
পেমেন্ট হয়নি      →  কুরিয়ার তুলবে অর্ডারের পুরো টাকা
```

অঙ্কটা **অর্ডার থেকে পড়া হয়**, ক্লায়েন্ট থেকে কখনো নয় — ইনপুট
হলে কেউ কম বসিয়ে দিত আর কুরিয়ার কম টাকা তুলে আনত।

## ক্রেতা যা দেখে

`POST /track` (অর্ডার নম্বর + ফোন) — কুরিয়ারের নাম, ট্র্যাকিং
নম্বর, অবস্থা, কখন পাঠানো হলো, কখন পৌঁছাল।

**ভেতরের আইডি যায় না:** `consignmentId` দিয়ে কুরিয়ারের API-তে কল
করা যায়, আর `courierAccountId` দিয়ে কোন অ্যাকাউন্ট সেটা জানা যায়।

পাঠানোর আগে `shipment` `null` — ভুয়া তথ্য দেখানোর চেয়ে কিছু না
দেখানো ভালো।

## অ্যাডমিনের দৈনিক কাজ

```
অর্ডার → ডিজাইন → প্রোডাকশন → ছাপা হলো
                                   ↓
                      [কুরিয়ারে পাঠান]  ← এক ক্লিক
                                   ↓
                   পার্সেল তৈরি + অর্ডার SHIPPED
                                   ↓
                   webhook আসতে থাকে (নিজে থেকে)
```

ছাপা হওয়ার আগে পাঠানো যায় না — রাইডার খালি হাতে ফিরলে কুরিয়ারের
খরচটা জলে যায়।

একই অর্ডার দুবার পাঠানো যায় না — দুজন রাইডার একই ঠিকানায় যেত আর
COD-র টাকা দুবার তোলার চেষ্টা হতো। ফেরত বা বাতিল হওয়া পার্সেল
গোনা হয় না, তখন আবার পাঠানোই উদ্দেশ্য।

`MANUAL`-এ webhook পাঠানোর কেউ নেই, তাই অ্যাডমিন হাতে বদলায়:
পিকআপ → পথে → পৌঁছেছে। API-ওয়ালা কুরিয়ারেও হাতে বদলানো যায় —
webhook হারিয়ে গেলে বা কুরিয়ার ফোনে জানালে।

## সেটআপ (একবার)

`.env`-এ:

```bash
# openssl rand -hex 32
COURIER_SECRET_KEY="<৬৪ অক্ষরের hex>"
```

তারপর সব অ্যাডমিন প্যানেল থেকে। প্রতিটা কুরিয়ারের মাঠগুলো:

| কুরিয়ার | মাঠ |
|---|---|
| Steadfast | `apiKey`, `secretKey` |
| Pathao | `clientId`, `clientSecret`, `username`, `password`, `storeId` |
| RedX | `accessToken`, `pickupStoreId` |
| Carrybee | `clientId`, `clientSecret`, `clientContext` |
| MANUAL | — |

**key ছাড়া অ্যাকাউন্ট বানানো যায়** (চুক্তি চলছে, key আসেনি), কিন্তু
**চালু করা যায় না**। চালু করতে দিলে সেটা ডিফল্ট হয়ে বসত আর প্রতিটা
অর্ডার পাঠানোর চেষ্টা ব্যর্থ হতো — অথচ প্যানেলে সব ঠিক দেখাত।

**বানান ভুল ধরা পড়ে:** `apikey` পাঠালে ৪০০, কারণ Steadfast-এ ওই
মাঠ নেই। চুপচাপ ফেলে দিলে অ্যাডমিন ভাবত সংরক্ষিত হয়েছে।

ডিফল্ট ঠিক একটাই — নতুনটা ডিফল্ট করলে পুরোনোটা আপনি সরে যায়।
