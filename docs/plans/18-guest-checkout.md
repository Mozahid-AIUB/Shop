# Phase 18 — Guest Checkout

> **অ্যাকাউন্ট ছাড়া কেনা।** বাংলাদেশে অনেক ক্রেতা রেজিস্ট্রেশন
> করতে চায় না; লগইন বাধ্যতামূলক রাখলে কিনতে আসা ক্রেতাও ফিরে যায়
> — আর সেটা কোথাও ত্রুটি হিসেবে দেখায় না, শুধু বিক্রি কম হয়।

## কেন এটা ঝুঁকিপূর্ণ ছিল

`Order.userId` nullable করা মানে ownership যাচাইয়ের **প্রতিটা**
জায়গা আবার দেখা। Prisma-তে দুটো ফাঁদ:

| লেখা | যা হতো |
|---|---|
| `where: { userId: undefined }` | Prisma শর্তটাই বাদ দেয় → **দোকানের সব অর্ডার** ফেরত আসে |
| `where: { userId: null }` | **সব গেস্ট অর্ডার** ফেরত আসে |

দুটোই ৫০০ দেয় না, চুপচাপ অন্যের ডেটা দেখিয়ে দেয়। তাই এখানে
টাইপ দিয়ে ঠেকানো হয়েছে, সতর্কতা দিয়ে নয়।

## নকশা — তিনটা অংশ

### ১. `CartOwner` — discriminated union

```ts
type CartOwner =
  | { kind: 'user'; userId: string }
  | { kind: 'guest'; guestToken: string };
```

`{ userId?: string; guestToken?: string }` লেখা হয়নি ইচ্ছাকৃতভাবে:
তাহলে "দুটোই আছে" আর "কোনোটাই নেই" দুটো অবস্থাই টাইপে বৈধ হতো,
অথচ দুটোই বাগ। union-এ সেগুলো লেখাই যায় না।

`where` ক্লজ **এক জায়গায়** বানানো হয় (`cartWhere`), তাই
`undefined` গলে যাওয়ার পথ নেই।

### ২. `@OptionalAuth()` — guard-এর তৃতীয় অবস্থা

`JwtAuthGuard` আগে দুটো অবস্থা জানত: সুরক্ষিত, আর `@Public()`।
গেস্ট route কোনোটাই নয় — টোকেন **থাকলে** যাচাই হতে হবে, না থাকলেও
চলতে হবে।

`@Public()` দিয়ে এটা করা যেত না: তখন guard টোকেন দেখতই না, আর
লগইন করা ক্রেতা নিজের কার্ট হারাত।

ভুল বা মেয়াদোত্তীর্ণ টোকেন **তবুও প্রত্যাখ্যাত হয়** — চুপচাপ
গেস্ট বানিয়ে দিলে ক্রেতা নিজের কার্ট খালি দেখে বুঝত না কী হলো।

### ৩. গেস্ট টোকেন

`POST /cart/guest` → `{ guestToken }`, ৩২ বাইট random (hex ৬৪ অক্ষর)।

- **সার্ভার বানায়, ক্লায়েন্ট নয়** — নইলে কেউ `guest-1`, `guest-2`
  পাঠিয়ে অন্যের কার্ট খুলত
- header-এ আসে (`x-guest-token`), cookie নয় — API আর web আলাদা
  origin-এ চললে third-party cookie ব্লক হয়ে কার্ট হারাত
- কার্টের row তখনই তৈরি হয় না; প্রথম আইটেম যোগ করলে হয়

## যা তৈরি হলো (API)

| Method | Path | কে | কী করে |
|---|---|---|---|
| POST | `/cart/guest` | সবাই | গেস্ট টোকেন দেয় |
| POST | `/cart/merge` | সদস্য | গেস্ট কার্ট নিজের কার্টে মেশায় |
| GET | `/cart` | সবাই | কার্ট; পরিচয় না থাকলে খালি |
| POST | `/cart/items` | সদস্য/গেস্ট | আইটেম যোগ |
| PATCH | `/cart/items/:id` | সদস্য/গেস্ট | পরিমাণ বদল |
| DELETE | `/cart/items/:id` | সদস্য/গেস্ট | আইটেম মুছে |
| POST | `/orders` | সদস্য/গেস্ট | চেকআউট |
| POST | `/coupons/validate` | সবাই | কুপন যাচাই |
| POST | `/track` | সবাই | অর্ডার নম্বর + ফোন দিয়ে দেখা |

**গেস্টের জন্য নয়:** `/orders` (তালিকা), `/orders/:number`,
`/orders/:number/cancel`, `/addresses/*` — সবই ৪০১। গেস্টের পরিচয়
নেই, তাই "তার" অর্ডার বলতে কিছু বোঝায় না।

## তিনটা সিদ্ধান্ত

### গেস্ট অর্ডার অ্যাকাউন্টে জোড়া হয় না

পরে একই ফোনে অ্যাকাউন্ট খুললেও পুরোনো গেস্ট অর্ডার সেখানে
দেখাবে না।

**কারণ:** রেজিস্ট্রেশনে ফোন যাচাই হয় না (OTP Phase 08-এ)। জোড়া
দিলে কেউ পরিচিতের নম্বর বসিয়ে অ্যাকাউন্ট খুলে তার কী কিনেছে আর
কোথায় থাকে সব দেখে ফেলত — নীরব তথ্য ফাঁস, কেউ কখনো জানত না।

গেস্ট `POST /track`-এ অর্ডার নম্বর **আর** ফোন দিয়ে দেখে — দুটোই
জানা লাগে, তাই অনুমান করে খোলা যায় না।

OTP হলে এটা আবার ভাবা যাবে।

### কুপন: `maxUsesPerUser: null` হলে গেস্টও পায়

| কুপনের সেটিং | কে পায় |
|---|---|
| `maxUsesPerUser: null` | সবাই, গেস্ট সহ |
| `maxUsesPerUser: 1` (ডিফল্ট) | শুধু লগইন করা ক্রেতা |

প্রতি-ক্রেতা সীমা গুনতে `userId` লাগে, গেস্টের সেটা নেই। চুপচাপ
সীমাটা উপেক্ষা করলে একজনই incognito খুলে পুরো ক্যাম্পেইন নিয়ে নিত।

ডিফল্ট `1` রাখা হয়েছে — অ্যাডমিন কিছু না বললে নিরাপদ নিয়মটাই
চলবে। ফেসবুক অ্যাডের কুপনে **স্পষ্ট করে** `null` দিতে হবে, যাতে
সিদ্ধান্তটা ইচ্ছাকৃত হয়।

ব্যবহারটা তবু লেখা হয় (`CouponRedemption.userId` = `null`), কারণ
অ্যাডমিনকে জানতে হবে ক্যাম্পেইনে মোট কত ছাড় গেল।

### গেস্টের বড় COD ঝুঁকির স্কোরে আসে

নতুন সংকেত `GUEST_LARGE_ORDER` — ১৫ পয়েন্ট, শুধু অঙ্ক বড় হলে।

নতুন অ্যাকাউন্টের (২০) চেয়ে **কম**, ইচ্ছাকৃতভাবে: গেস্ট চেকআউট
আমরা নিজেরাই খুলেছি বিক্রি বাড়াতে, সেই দরজা দিয়ে ঢোকার জন্য
ক্রেতাকে বেশি শাস্তি দেওয়া স্ববিরোধী হতো।

ছোট অর্ডারে ধরা হয় না — নইলে প্রতিটা গেস্ট অর্ডারে সতর্কতা আসত
আর অ্যাডমিন তালিকাটা পড়াই বন্ধ করে দিত।

**গেস্টের ইতিহাস ফোন ধরে গোনা হয়**, `userId` ধরে নয়। এটা আসলে
শক্ত সংকেত: নতুন অ্যাকাউন্ট খোলা সহজ, নম্বর বদলানো কঠিন।

## অ্যাডমিন প্যানেলে

গেস্ট অর্ডার সদস্যের অর্ডারের মতোই দেখায় — নাম, ফোন, ঠিকানা,
পণ্য, টাকা, ঝুঁকির স্কোর। পার্থক্য একটাই: বিস্তারিত পাতায়
`user` `null`।

ক্রেতার নাম-ফোন `shipFullName`/`shipPhone`-এ থাকে (অর্ডারে কপি
হয়ে যায়), তাই অ্যাকাউন্ট না থাকলেও পাঠানোর আর ফোন করার সব তথ্য
মালিকের কাছে থাকে।

## ফ্রন্টএন্ডের জন্য

1. অ্যাপ চালু হলে `localStorage`-এ গেস্ট টোকেন আছে কিনা দেখো
2. না থাকলে **কার্টে প্রথম কিছু যোগ করার সময়** `POST /cart/guest`
   ডেকে টোকেন নাও আর জমিয়ে রাখো (আগেই ডাকলে শুধু ঘুরতে আসা
   লোকের জন্যও অর্থহীন call যেত)
3. প্রতি request-এ `x-guest-token` header পাঠাও
4. **লগইন বা রেজিস্টারের পরপর `POST /cart/merge` ডাকো**, গেস্ট
   টোকেন header-এ রেখেই। এটা না ডাকলে ক্রেতা কার্ট ভরে লগইন
   করার পর কার্ট খালি দেখত — আর সেটা ঠিক সেই মুহূর্তে, যখন সে
   কিনতে সবচেয়ে কাছে
5. মেশানোর পর localStorage থেকে গেস্ট টোকেন মুছে দাও — সার্ভারে
   কার্টটা আর নেই, আর লগইন থাকলে টোকেন এমনিতেও উপেক্ষা হয়

### কার্ট মেশানোর নিয়ম

| অবস্থা | যা হয় |
|---|---|
| দুই কার্টে আলাদা পণ্য | সব এক কার্টে আসে |
| দুই কার্টে **একই** পণ্য | পরিমাণ **যোগ** হয় (২ + ৩ = ৫) |
| যোগফল স্টকের বেশি | স্টকেই থামে, ত্রুটি দেয় না |
| পণ্যের বিক্রি বন্ধ হয়ে গেছে | বাদ পড়ে |
| গেস্ট টোকেন নেই বা ভুল | নিজের কার্টই ফেরে, ত্রুটি নয় |

যোগ করা নিখুঁত নয় (ক্রেতা হয়তো ২টাই চেয়েছিল), কিন্তু "কম
দেখানো"-র চেয়ে "বেশি দেখানো" ভালো: সংখ্যা কমানো এক ক্লিকের কাজ,
হারিয়ে যাওয়া পণ্য সে আর খুঁজেই পেত না।

স্টকের সীমায় থামে কিন্তু **ত্রুটি দেয় না** — লগইনের মুহূর্তে
"স্টকে মাত্র ২টা" বলে পুরো মেশানো আটকে দিলে ক্রেতা বাকি
পণ্যগুলোও হারাত। চেকআউট এমনিতেও স্টক আবার যাচাই করে।

গেস্ট কার্ট মেশানোর পর **মুছে ফেলা হয়**, নইলে আবার ডাকলে
পরিমাণ দুবার যোগ হতো।

আটকাত; এখন অ্যাকাউন্ট মুছলে অর্ডারটা গেস্ট-অর্ডারে পরিণত হয়।

বাঁচতে হবে**। নইলে ক্রেতা অ্যাকাউন্ট ডিলিট করলে দোকানের আয়ের
হিসাব থেকেও অর্ডারটা মুছে যেত।
